# Обновление Hangar одной командой

Для существующей установки Matthew62s/plane-time-tracking в `/opt/hangar`:

```bash
hangar-update update
```

Скрипт `scripts/hangar-update.py` не требует реестра образов или токенов:
исходники берутся из `preview`, образы собираются локально с использованием
Docker build cache. Процесс рассчитан на один сервер с Docker Compose v2,
Python 3.10+, Git и существующим `/opt/hangar/runtime/hangar-compose`.
SSH-доступ скрипту не нужен: его запускают непосредственно на сервере.

## Однократная установка

Выполнять **после слияния PR с этим скриптом в `preview`**. `/opt/hangar` не должен
становиться Git-репозиторием; исходники инструмента хранятся отдельно:

```bash
mkdir -p /opt/hangar/tools
git clone --branch preview --single-branch \
  https://github.com/Matthew62s/plane-time-tracking.git \
  /opt/hangar/tools/updater
install -m 0755 /opt/hangar/tools/updater/scripts/hangar-update.py \
  /usr/local/sbin/hangar-update

hangar-update plan
```

Если каталог инструмента уже существует, не перезаписывать его вслепую: проверить
его `git status`, затем обновить через `git pull --ff-only origin preview` и
повторить `install`. Инструмент не обновляет собственный код автоматически.

`plan` показывает компоненты для сборки и работающие сервисы для обновления.
Он не собирает образы, не меняет wrapper и не пересоздаёт контейнеры.

Проверить адрес сайта при первом запуске:

```bash
hangar-update update --url https://plane.iage.net
```

В дальнейшем `--url` можно опустить, если `APP_BASE_URL` или `WEB_URL` в
действующей конфигурации API содержит правильный публичный origin.

## Что происходит при обновлении

1. Блокировка не позволяет запустить два обновления/отката этим инструментом
   одновременно. Не запускать параллельно ручные команды Compose.
2. В отдельный каталог загружается `preview`, фиксируется точный commit SHA.
   Собираются все установленные компоненты: API, web, admin, space, live, proxy.
   У каждого образа свой локальный тег; чужие registry-теги не перезаписываются.
   Вывод сборки сохраняется в `build.log` внутри каталога обновления.
3. На новом API-образе выполняется `manage.py migrate --check`. Если есть
   неприменённые миграции **или ошибка проверки**, скрипт останавливается до
   переключения контейнеров. Миграции требуют отдельного плана обновления;
   этот инструмент не применяет и не откатывает изменения схемы автоматически.
4. В `/opt/hangar/deploy-state/<дата>-<pid>/` сохраняются текущая конфигурация
   `runtime`, dump PostgreSQL и метаданные обновления. Пароль берётся внутри
   контейнера БД, без запроса в терминале. Архив проверяется через `pg_restore --list`.
   Эта проверка подтверждает читаемость оглавления, но не заменяет пробное
   восстановление БД в отдельном окружении.
5. Для текущих работающих контейнеров сохраняются отдельные локальные теги
   предыдущих образов. Добавляется `compose.hangar-update.json` с выбором образов,
   а wrapper получает дополнительный `-f`. Все его прежние аргументы, включая
   `plane.env`, `compose.caddy.yml`, `compose.smtp.yml` и override отчёта,
   сохраняются. Секреты не копируются в командную строку или вывод скрипта.
6. Пересоздаются только выбранные **работающие** сервисы приложения. Образ API
   обновляется также у worker, mail-worker, beat-worker, import-worker и migrator;
   остановленные сервисы не запускаются, migrator не выполняется автоматически.
   Контейнеры PostgreSQL, Redis, RabbitMQ и хранилища не пересоздаются.
7. Проверяются образы работающих контейнеров, их Docker healthcheck при наличии,
   HTML главной страницы и JSON `/api/instances/` через публичный адрес с обычной
   проверкой TLS. При ошибке переключения или проверки готовности скрипт пытается
   вернуть сохранённые образы. Если откат тоже не удался, он сообщает об этом
   и сохраняет каталог для диагностики.

После успеха проверить под своей учётной записью нужную функцию приложения:
общая проверка готовности не заменяет проверку отчёта, почты или интеграций.
Пересоздание контейнеров может вызвать короткий перерыв в работе.

Для изменения только отчёта или frontend можно явно сузить область:

```bash
hangar-update update --components api web
# Только web, если backend и общие API-контракты не менялись:
hangar-update update --components web
```

Сужать область следует осознанно: изменение общих пакетов может затронуть
несколько приложений. По умолчанию обновляются все установленные компоненты.

Можно указать полный SHA уже слитого в `preview` коммита:

```bash
hangar-update update --ref cf6473c03089b78d0116fc8517c84fe005e95385
```

Произвольные ветки и SHA, не входящие в историю `preview`, не принимаются.
При этом локально проверенные source/build состояния не означают, что конкретный
коммит прошёл GitHub CI: перед обновлением оператор проверяет результаты PR.

## Состояние и откат

```bash
hangar-update status
hangar-update rollback
```

`rollback` работает и в новой SSH-сессии: записи сохраняются на диске, shell-переменные
из предыдущего запуска не нужны. Откатывается последнее обновление, дошедшее до
переключения контейнеров. Повторный откат уже отменённого обновления ничего не меняет.
Выбор образов сохраняется в управляемом override, поэтому последующий вызов обычного
`runtime/hangar-compose` использует те же образы и сохраняет SMTP-настройки.

База при откате **не восстанавливается**: новые пользовательские записи остаются.
Скрипт не выполняет downgrade схемы, `down -v`, очистку volumes или Docker prune.
Копия `runtime` и dump содержат чувствительные данные; каталог обновления создаётся
с закрытыми правами. Не публиковать его содержимое в Git или чатах. Для защиты
от потери диска дополнительно сохранять резервные копии за пределами сервера.

Старые каталоги, исходники и образы автоматически не удаляются. Следить за местом
на диске и вручную удалять только заведомо ненужные сборки и копии после проверки
внешнего резервного копирования. Не удалять образы и каталог, нужные для отката.

## Разработка инструмента

```bash
python3 -m unittest discover -s scripts/tests -p 'test_hangar_update*.py' -v
```

Unit-тесты моделируют границы Git/Docker/Compose: отказ сборки, проверки миграций,
резервного копирования, запуска и готовности; ручной и автоматический откат;
сохранение SMTP-wrapper, непричастных overrides, блокировку параллельных запусков
и отсутствие секретов в сообщениях об ошибках. Эти тесты не подключаются к
рабочему серверу. Проверка на реальном сервере остаётся отдельным действием.

Интеграционная проверка с настоящим PostgreSQL и небольшими тестовыми приложениями:

```bash
HANGAR_UPDATE_DOCKER_TEST=1 python3 -m unittest discover \
  -s scripts/tests -p 'test_hangar_update_docker.py' -v
```

Она создаёт собственный временный Git-репозиторий и Compose-проект со случайным
именем, собирает fixture-образы, проверяет реальный dump, переключение образов,
HTTP-готовность, откат и остановку перед неприменёнными миграциями. В конце удаляет
только свои контейнеры и volumes. Это проверка механизма развёртывания, а не сборка
полного Hangar и не проверка конфигурации рабочего сервера. В GitHub Actions
запускаются и unit-, и интеграционные проверки.
